# 团队 Agent 工作流程

本流程适用于所有开发、修复、重构、审查和规范维护任务。技术细节以[项目规范](guides/project.md)及对应的[后端](guides/backend.md)、[前端](guides/frontend.md)规范为准。默认用中文沟通，代码标识符和提交主题遵循项目既有英文约定。

## 接手任务

1. 读取根入口及适用的规范，确认任务目标、受影响模块和可验证的完成条件。复杂任务用简短步骤说明范围；简单修改直接执行。
2. 在实际工作目录运行 `git status --short`，按需要查看差异，识别已有修改和未跟踪文件。保留用户及其他 Agent 的工作，不擅自覆盖、还原、暂存或提交。
3. 优先用 `rg` 查找入口、现有实现、公共能力和所有调用者。先理解真实流程，再确定修改位置。
4. 修复缺陷先确认根因；涉及共享函数时检查所有调用者。跨层变更沿 UI/API → DTO → Service → Mapper/SQL 的实际路径核对，并检查权限、导入导出、国际化和测试资源的影响。
5. 优先读取 `pom.xml`、`package.json`、锁文件和实际配置。文档与实现不一致时记录差异，不猜测命令、返回结构或不存在的文件。

## 实现

- 在任务范围内持续推进。可逆的本地检查和修改直接完成；只有缺少关键事实或授权时才提问，等待期间继续不依赖答案的工作。
- 优先复用现有工具、组件、类型和安装的依赖，再考虑标准库和平台能力。仅为已确认的需求新增代码；不附带依赖升级、框架替换、目录重构或无关格式化。
- 保持前后端模块依赖方向和业务边界；同步修改受到影响的 DTO、API 类型、Mapper XML、数据库迁移、权限资源和中英文文案。
- 业务行为改变时补充针对性测试；优先使用现有 JUnit、Spring Boot Test 和 Testcontainers。纯规范或配置修改使用对应自检，不为此添加业务测试。
- 保留输入校验、权限/数据范围检查、事务原子性、错误处理和基本可访问性。注释说明业务意图与边界，逻辑块合理留白。
- 不手工编辑生成产物或前端锁文件，不改写已发布迁移。必须新增依赖时按现有工具生成锁文件并审查差异。
- 不使用 `git reset --hard`、`git clean`、强制 checkout 或整仓还原清除他人的工作。自动修复仅针对本次文件；检查修复前后的差异，不用整仓格式化掩盖问题。

## 授权与执行

- 用户明确要求的动作及已经给出的授权持续有效；不要在实现和检查完成前反复要求确认。
- 未获得任务授权时，不提交、推送、合并、发布、部署或向外部人员发送消息。需要授权的最终动作，应先完成可审查的变更和验证，再说明具体动作及影响。
- 沙箱或审批拒绝时，保留已完成工作，使用安全替代方式继续。不得改用别名、参数排列、脚本、其他工具或放宽配置绕过限制。
- 不在日志、测试夹具、截图、Issue 或 PR 中输出真实凭据、客户数据、IP 地址或未脱敏日志。

## 多人或多 Agent 协作

常规任务由当前 Agent 完成。需要且已获授权的并行协作，统一使用本目录的规范正文，并遵守以下分工：

| 职责 | 负责内容 | 交接内容 |
| --- | --- | --- |
| 任务负责人 | 明确验收条件、划分文件范围、协调共享修改、整合结果 | 最终差异、整体验证和未解决事项 |
| 后端执行者 | Java、Mapper、迁移、权限和后端测试 | 修改文件、契约影响、测试结果 |
| 前端执行者 | Web/Mobile、共享类型、路由、交互和国际化 | 修改文件、两端影响、检查和截图 |
| 审查者 | 对照需求与项目规范检查回归风险 | 有证据的发现、位置、影响及验证缺口 |

- 派发任务时附上目标、允许修改的文件/目录、验收条件、必要上下文及验证命令。子 Agent 同样读取根入口和领域规范，不复制一套规则到任务提示中。
- 每个文件只有一个写入负责人。共享 DTO、API 类型、锁文件、POM、权限和迁移由负责人协调；发生重叠时先调整分工再修改。
- 共享工作区时不同时运行会改文件的格式化、依赖安装、Git 操作或抢占同一输出目录的构建。需要独立检出时使用 worktree，并说明已有修改是否进入任务。
- 审查默认只读，不擅自把发现改成实现。执行者交接修改范围、已运行命令及结果、接口或迁移影响和剩余问题。
- 任务负责人审查合并后的完整差异，运行与最终变更范围相符的检查；不能把单个子任务通过当作整体通过。

## 验证与交付

按[验证矩阵](verification.md)选择最小但充分的检查范围。缺陷修复应有能复现问题的回归验证；共享层、权限或跨端变化扩大到实际受影响的消费者。

交付前检查差异与验收条件，运行 `git diff --check`，确认没有混入已有修改、敏感数据、生成产物或无关格式化。按需遵循仓库 PR 模板，说明文档影响，可见界面修改准备截图。

最终交付简明列出：修改内容及文件、实际运行的验证及结果、未完成检查与原因、必要的接口/迁移/部署注意事项。未运行、失败和已知基线问题分别说明；不得把跳过测试的构建称为测试通过。
