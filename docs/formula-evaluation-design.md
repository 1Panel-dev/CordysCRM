# 表单公式 Java 求值与创建链路设计

## 当前实现与明确边界（2026-09-09）

Java 公式计算仅供 MCP tools 内部使用，不改变 CRM 原有新增、更新、导入、批量更新及历史小数调整的行为。

- MCP 的 `buildAddParam/buildUpdateParam` 完成字段解析、默认值及更新旧值合并后，含公式时调用独立 `/mcp/formula/prepare`，成功后才提交原业务接口。该入口只计算请求副本，不落库、不读取目标记录；表单定义来自当前组织，来源名称查询保留权限校验。
- 写入计算前验证完整 IR（包括未命中的惰性分支）、节点、函数参数数量和引用身份。无效定义及数据源显示值解析失败会阻止保存，并经 Translator 返回校验错误；合法空文本结果仍可使用。
- 设计器保存时同步执行 diagnostics，错误公式不向表单属性提交。前端数值截断先展开科学计数法，避免指数被字符串截掉。
- `FormulaRequestBodyAdvice` 已移除；动态表单 Service 不再调用求值器，也不为公式合并旧字段；固定批量限制已移除，动态批量恢复原批量路径。MCP 更新仍须在工具内读取完整旧记录，保留编号和子表行身份，补全全部输入后计算。
- Java 公式能力用于便利 MCP 写入，不扩展主工程统一响应：`ResultHolder` 保持原样，不增加计算证据字段、响应头或 AI 参数。MCP 保持原有读回复核，不在 MCP 再实现求值器。Cockpit 的存在性/普通字段复核放宽是用户明确选择的策略，不作为漏洞，不因公式功能收紧；该复核不等于独立证明公式算法正确，算法正确性由单测保障。
- MCP 求解器结果按配置向零截断；CRM 原有 Resolver 显示规则与历史精度调整保持原样。数据源公式只读取同组织、当前用户可读且存在的来源，缺失/越权/未知选项失败关闭。
- 专用入口隐藏于 OpenAPI，不提升为独立大模型工具；内部只有 `formKey + values`，更新模式由载荷中的记录 ID 确定，不增加公式、时区或当前时间等 AI 入参。普通 CRM 写入不调用此入口。
- 当前仍采用分组拓扑：支持行内依赖及顶层聚合；子表依赖其它作用域的计算字段拒绝，避免读取旧值及漏检跨层环。此限制仅作用于 MCP 求解，不施加到 CRM 原有写入链路。

回归入口：`FormulaDefinitionValidationTest`、`FormulaCompletionServiceTest`、`CustomFormDataServiceTest`，以及 `node frontend/packages/web/scripts/formula-number.test.mjs`。后者直接提取并执行生产截断函数，覆盖科学计数法、负数、浮点尾差和非有限数值。

## 历史设计与备选方案（不代表当前接入方式）

以下保留早期设计与备选方案供评审追溯。实际行为以本文顶部“当前实现与明确边界”为准，不能据此恢复全局补齐或重算。

- 支持前端当前函数：`SUM`、`DAYS`、`CONCATENATE`、`TEXT`、`IF`、`IFS`、`AND`、`TODAY`、`NOW`。
- 支持算术、比较、主表字段、子表当前行和子表列聚合。
- 只执行公式 JSON 中的白名单 IR，不执行 `source` 文本、SpEL 或任意脚本。
- 公式和字段类型取当前组织的实时表单配置；已覆盖的写入入口按完整输入权威计算，不信任客户端公式结果。
- 数值公式结果按字段精度向零截断，不做四舍五入，与前端 `keepDecimal` 保持一致。
- 流水号的生成机制不在本次范围内；新建时公式引用流水号仍输出现有 `${字段名}` 占位符，由原流水号流程替换。
- 不给 AI 增加公式、时区、当前时间、字段元数据等参数。MCP 仍只提交既有的 `module + fields`。

## 核心结构

`FormulaEngine` 是无业务模块依赖的封闭 IR 求值器，输入为公式 JSON 和内部构造的 `FormulaEvaluationContext`，输出一个 Java 值。`FormulaCompletionService` 负责读取整张表单数据、建立字段元数据、按依赖顺序计算子表及主表公式，并把结果写回业务字段或 `moduleFields`。

时区不作为方法或 AI Tool 参数。Java 使用应用进程默认时区，前端使用浏览器本地时区，两者并非天然相同；一次 `complete` 只捕获一次当前时间，保证该记录的 `TODAY`/`NOW` 一致。部署环境需统一时区。MCP 不重新求值；不保证跨时区浏览器的实时预览与提交瞬间完全相同。

## 历史方案：RequestBodyAdvice 按需补齐（已被上述权威计算取代）

创建请求的处理顺序是：

1. Spring 把 JSON 反序列化成现有 AddRequest。
2. `FormulaRequestBodyAdvice` 根据新增 API 路径确定表单类型，读取服务端实时表单，只补齐请求中没有值的公式字段。
3. Jakarta Bean Validation 校验补全后的请求，因此公式生成的 `@NotBlank` 业务字段不会被提前拒绝。
4. 业务 Service 正常创建资源。
5. 业务 Service 直接保存请求中的公式值，保存层不再重算。

更新请求同样支持公式补全：

1. MCP 更新在提交前按记录 ID 回读当前记录，补全模型未显式提交的可写字段。
2. `FormulaRequestBodyAdvice` 对已登记的 `/update` 路径使用 `createMode=false` 计算，使公式生成的必填业务字段能在 Bean Validation 前获得值。
3. 前端已计算的公式值保持不变；MCP 不提交公式字段，由服务端补齐缺失值。
4. 更新模式引用流水号时使用 MCP 回读后提交的已有值，不生成新增阶段的 `${字段名}` 占位符。

MCP Tool Schema 仍为 `module + id + fields`，不增加公式、时区、当前时间或表单元数据参数。

浏览器仍会实时计算、展示公式结果，并在点击提交前带上当前值；只要该值非 `null`，服务端就不再计算或覆盖。

### 改动点

- 新增通用 IR、解析器、求值器、结果归一化器和整表补全服务。
- 新增一个全局但只匹配已登记 `/add` 和 `/update` 路径的 `RequestBodyAdvice`。
- 新增写请求 DTO 的通用 Bean 属性适配，不改变各 AddRequest、UpdateRequest 和 MCP Tool Schema。
- 保存层不接入公式求值，避免前端结果被二次计算。

### 优点

- 不需要修改所有 Controller、AddRequest 和 MCP 服务。
- 能在现有 `@Validated` 执行前补齐公式生成的必填业务字段。
- 普通前端、MCP 和其它 HTTP 客户端共用同一套逻辑。
- 对现有公开 API 和 AI 入参零增量。

### 缺点与约束

- API 路径到 `FormKey` 的映射集中维护，新增表单模块时必须登记。
- Advice 属于横切机制，调用点不如 Controller 显式。
- 客户端提交了过期或伪造的公式值时，服务端会直接保存；这是取消权威重算后的明确取舍。
- 只覆盖已登记的 HTTP 新增和更新请求；导入不接入本次公式补全或拦截，保持原有逻辑。定时任务等其它非 HTTP 入口不在当前覆盖范围内。

## 备选方案 A：显式创建业务管线（长期推荐）

为所有动态表单创建统一的 `CreateFormRecordPipeline`：规范化输入、公式补全、动态必填校验、业务 DTO 映射、保存。Controller 和 MCP 最终都调用这条管线；移除会在公式计算前触发的静态业务字段 `@NotBlank`，改为表单感知的动态校验。

### 改动点

- 抽取统一创建命令和管线接口。
- 各模块 Service 逐步迁移到管线。
- 将动态表单字段的静态 DTO 校验迁移为公式计算后的统一校验。
- 导入、OpenAPI、MCP 等入口统一接入。

### 优点

- 执行顺序显式，容易调试、审计和扩展。
- 只计算一次，可以固定同一次 `evaluationNow`。
- 从根本上统一静态 DTO 校验和动态低代码表单规则。

### 缺点

- 改动范围最大，涉及多个业务模块及回归测试。
- 迁移期间新旧创建链路需要并存。
- 不适合作为本次问题的低风险热修方案。

## 备选方案 B：Controller 显式前置计算 + 手动校验

各新增 Controller 取消参数上的自动 `@Validated`，在方法内部先调用公式补全，再显式调用 `Validator`，然后进入 Service。

### 优点

- 调用点直观，不使用全局 Advice。
- 可以按模块定制异常和日志。

### 缺点

- 每个新增接口都要修改，容易漏掉新模块、导入接口或特殊创建入口。
- Controller 重复模板代码，执行顺序依赖开发规范。
- 仍需保存层兜底防止非 Controller 入口绕过。

## 备选方案 C：CRM 内部公式预计算 API，由 MCP 调用

CRM 提供不暴露给 AI 的内部接口：输入 `formKey + 已映射的当前表单值`，输出补全后的值。MCP 在调用真实 `/add` 前先调用该接口，再把结果合并到 AddRequest。AI Tool Schema 仍保持 `module + fields`。

### 优点

- CRM 继续维护唯一 Java 求值器，MCP 不复制公式实现。
- 不使用 RequestBodyAdvice，MCP 创建能通过现有 Bean Validation。
- 内部请求参数可由程序构造，不增加大模型生成错误的机会。

### 缺点

- 每次 MCP 创建增加一次网络请求和一个失败点。
- 只解决 MCP；普通 API 客户端、导入等仍需各自接入。
- 需要设计内部接口鉴权、值映射和版本兼容。
- 计算后到实际保存之间表单配置可能发生变化，因此保存层仍应兜底。

## 备选方案 D：每个 AddRequest 定制反序列化器

通过 Jackson 反序列化器在 DTO 构造阶段补全公式，使结果天然早于 Bean Validation。

### 优点

- 执行时机满足要求，不依赖 Controller。
- 可针对单个 DTO 精细控制。

### 缺点

- 反序列化层需要访问组织上下文、数据库和业务解析器，职责混杂。
- 每种请求 DTO 都要注册或维护适配，测试复杂。
- JSON 解析失败与业务公式失败难以清晰区分。

因此不建议采用。

## 方案对比与建议

| 方案 | AI 参数变化 | 覆盖入口 | 改动量 | 调用显式性 | 建议 |
|---|---:|---|---:|---|---|
| RequestBodyAdvice 按需补齐 | 无 | 已登记的 HTTP 新增/更新 | 小 | 中 | 当前可交付方案 |
| 显式创建业务管线 | 无 | 可覆盖全部 | 大 | 高 | 长期目标架构 |
| Controller 前置计算 | 无 | 逐个 HTTP 接口 | 中 | 高 | 模块少时可选 |
| MCP 内部预计算 API | 无 | MCP | 中，跨仓库 | 高 | 仅需解决 MCP 时可选 |
| DTO 反序列化器 | 无 | 指定 DTO | 中 | 低 | 不建议 |

建议本次使用已实现的 RequestBodyAdvice 按需补齐方案；后续若项目要统一导入、自动化和 API 创建流程，再迁移到“显式创建业务管线”。迁移时核心 `FormulaEngine` 与 `FormulaCompletionService` 无需重写，只替换触发位置。
